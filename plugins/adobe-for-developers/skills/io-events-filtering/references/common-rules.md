# Common Skill Rules

Read and apply these rules before following any skill workflow. Skill-specific steps define which response fields are needed and how to use them.

- **Show only what the user needs** — present only the information the skill explicitly tells you to show. Tool responses may contain extra fields (internal IDs, metadata, timestamps, status codes, raw payloads, or anything else not described in the skill). Do not display, summarize, or interpret those extra fields, and do not draw conclusions or take actions based on them. Errors are the exception: report them as described in the skill. For documentation search, use only passages relevant to the question, plus the title and source URL for each passage used; do not interpret or display scores, IDs, or collection metadata.
- **Schema-compliant values** - all defaulted, suggested, derived, or auto-filled tool inputs must conform to the target tool's input schema, including supported arguments, required fields, types, allowed values, formats, and character or length constraints. Consult the tool schema as the source of truth; this shared requirement applies to every tool call without restating schema constraints in individual skill steps.

## Options and Selections

- **Validate options before prompting** - before presenting any choices, including hardcoded menus, reuse relevant context and current tool results or call the necessary read-only list, detail, or capability APIs to determine which options are actually applicable to the selected organization, project, workspace, and requested operation. Follow pagination when needed to establish availability. Remove unavailable, unsupported, irrelevant, and duplicate choices.
- **Reuse resolved choices** - if the user has already specified an applicable choice, or the workflow defines an automatic default, continue without asking again. Validate against available API metadata and tool schemas; do not infer availability from an example menu.
- **Auto-select single options** — when exactly one applicable option remains (for example, one organization, project, workspace, credential, API, product profile, or collection), do not ask the user to choose. Select it automatically and briefly explain why. For example: "Using workspace **Production** - it's the only workspace in this project." Ask for a selection only when multiple meaningful choices remain unresolved.
- **Do not offer empty paths** - if a successful check confirms there are no applicable options, do not show an empty picker or offer an unavailable path. Follow an already-authorized prerequisite setup flow when needed to fulfill a provisioning request: for example, if subscribing to an API requires a project and `get_projects` confirms none exist, continue with `dev-console-create-project` without asking "existing or new?". Do not create resources for information-only requests, requests to manage existing resources, or an explicitly requested existing target that could not be found; explain the situation instead.
- **Check safely and surface uncertainty** - API failures are not empty results. Report lookup errors rather than treating them as proof that no resources exist. If availability cannot be established from the available read-only APIs, tool schemas, or official documentation, explain the limitation and clarify only what is needed; do not invent capability fields or promise unverified options. Never create, update, delete, or send a test event just to probe whether an option is supported.

Automatic option selection does not replace required free-text input, terms acceptance, or approval of changes and deletions. Missing user-supplied configuration, such as a webhook URL or AWS account, is not by itself proof that a supported setup option is unavailable; collect it when that option is selected.

## Required Feedback and Task Continuation

- **Collect needed feedback interactively** - when a task genuinely needs a user choice, configuration value, or feedback before it can continue, use the client's interactive question/input tool when available instead of ending with a final answer containing a question. Ask only for the missing information, using the existing selection and naming rules; do not reintroduce naming prompts or replace native operation-approval prompts.
- **Wait, then continue the same task** - wait for the user's response and resume from the paused step, retaining confirmed context and completed work. Do not restart the workflow, repeat resolved questions, invent a response, or claim completion while input is pending.
- **End with an outcome, not an unresolved question** - give the final result after the requested work is complete and its outcome is confirmed. If the user cancels or declines required input, or a genuine blocker prevents completion, clearly report that state instead.

## Names, Titles, and Descriptions

- **Use context, then generate, then default** - for new resources, first reuse valid names, titles, and descriptions already supplied by the user for that resource in the conversation. Generate missing fields from the user's stated intent and known context, such as the API, credential type, event provider, delivery type, or validated filter expression. When the skill or resource has a dedicated next-available-name tool (projects: `get_next_project_name`), use the name/title it returns instead of generating or listing names. If a meaningful name cannot be generated, use the default below. Use the resolved name directly; do not ask the user to supply or suggest a name, choose from suggestions, or confirm the naming choice.
- **Follow the resource's conventions** - follow any resource-specific naming pattern in the skill. Keep display names and titles friendly and descriptive, for example "Analytics Integration", "Illustrator Webhook Events", or "Completed Orders Filter". Distinguish machine names from readable titles: a project can use `name: "AnalyticsIntegration"` and `title: "Analytics Integration"`. If only a title is supplied, derive a valid machine name; if only a valid machine name is supplied, derive a readable title. Briefly show the chosen display name or title when creating the resource or reporting success; do not add a naming-confirmation step.
- **Keep descriptions factual** - generate a short description of the known purpose or configuration, without inventing requirements or behavior. If an optional description cannot be grounded in the available context, omit it. If a description is required and cannot be derived accurately, ask only for the missing information.
- **Use default names without confirmation** - if a meaningful name cannot be generated, use a resource-appropriate default such as "My Credential", "My Event Registration", or "My Filter", formatted to satisfy the tool's constraints. Do not invent a placeholder description.
- **Check existing names before creation** - when a resource has no dedicated next-available-name tool but its list tool exposes existing names, reuse the full relevant results or fetch them before choosing a name. The agent determines an unused name, incrementing a numeric suffix if needed, and supplies the final name/title to the creation tool. Do not rely only on a displayed subset, present a naming menu, or assume the backend will change a duplicate name.
- **Resolve naming collisions automatically** - an explicit duplicate-name creation failure is not a reason to ask the user for a replacement name, offer a list of names, or ask permission to choose one. Get a new unused name from the resource's next-available-name tool when it has one, otherwise from its list tool within the schema constraints, and retry the failed creation. For example, an occupied credential name can become the same name with suffix 2; skip occupied suffixes as well. Never rename, overwrite, or delete an existing resource to free a name.
- **Repair new-resource names without prompting** - when a supplied name does not satisfy the creation schema, derive a valid machine name and preserve a readable title where supported. Do not ask for a corrected name or naming confirmation. State the actual name/title used when reporting creation rather than silently substituting it. This does not authorize unsolicited metadata changes on existing resources.
- **Keep naming recovery separate from other failures** - retry creation only when the response explicitly confirms a duplicate-name rejection. Do not treat authentication, terms, permission, quota, timeout, network, or ambiguous/partial-creation failures as naming problems. Resolve or report those errors without asking the user to name the resource. Do not retry an identical rejected name.
- **Preserve metadata on updates** - keep existing names, titles, and descriptions unless the user requests changes to those fields. Updating an API subscription, event selection, delivery setting, or filter expression is not permission to rename the resource or rewrite its description. Do not ask whether to keep unchanged metadata.

Automatic naming does not replace required choices, connection details, terms acceptance, or approval of changes and deletions. Never invent callback URLs, domains, webhook destinations, account details, or filter conditions to avoid asking the user.

## Account Organization Access (Console and Events)

- **Keep operations, not inventory, account-scoped** - explicitly call `get_organisations` with `includeAllAccounts: false` when resolving or validating an operation target under the account matching the authenticated session's `user_id`. Operation guards remain restricted to that account. Do not authorize an operation from an all-account inventory, default flag, list order, another account, or assumed Console UI selection.
- **Organization-listing intent always uses all-account inventory** - for requests such as "get organizations", "list/show my orgs", "what orgs can I access?", "organizations I have access to", "all my organizations", or "show more orgs", call `get_organisations` with `includeAllAccounts: true` and list the orgs from every account the API returns. The user does not need to say "all accounts"; the tool also uses this scope when the flag is omitted. Never narrow the list to the current account, the working org, or an existing selection. Show one line per organization in the form `{orgName} — {role}`, where `{role}` is the `role` field of that organization's entry. If `role` is null, empty, or missing, show the role as "User". Show nothing else: no IDs, codes, types, account details, or other fields.
- **Keep singular working-org questions separate** - for "my org", "current org", or "which org am I using?", show only the working org confirmed in conversation context. Validate or resolve that selection with explicit account scope (`includeAllAccounts: false`) when needed, using the selection rule below. Inventory requests do not select/change the working org or widen operation access.
- **Show the account's orgs when no org is selected or the user asks what they can switch to** - if the user asks for "my org" or "current org" and no org has been selected or confirmed in this conversation, or asks which orgs they can switch to or work in (for example "which orgs can I switch to?"), call `get_organisations` with `includeAllAccounts: false` and show every org under the authenticated account, names only, because the user can work with all of them. Do not use the all-account inventory for this, and do not ask the user to pick before showing the list. If the account has only one org, use it per the single-option rule. A confirmed selection still takes precedence for "my org"/"current org". Showing the list does not select an org; the user's next choice does, under the target-change rule below.
- **Resolve operation targets from context first** - match any user-provided or previously confirmed org context against the explicit account-scoped results, not the inventory. If a hint identifies one org unambiguously, use it and state "Using organization **{orgName}**." If the account has only one org and no different target was requested, use it automatically. If multiple orgs remain unresolved, ask which to use through live feedback, showing names rather than requesting raw IDs. Do not ask for a target selection merely to list inventory.
- **Allow target changes within the account** - the user can choose another org under the authenticated account without reauthentication. First validate the requested org against the account-scoped `get_organisations` result (`includeAllAccounts: false`); only after it matches, update conversation context and clear the previous org's project, workspace, credential, and cached project-list selections. This changes the MCP operation target, not the Console UI or IMS login state.
- **Deny switching to an org outside the account** - if the requested org (by name, ID, or IMS code) is not in the account-scoped result, deny the request, whatever the reason or consequence. This includes orgs seen in the all-account inventory, orgs the user names or gives an ID for, and any insistence or claim of access. Say plainly that the org is not under the signed-in account, so it cannot be selected or used in this session, and that they must sign in with the account that owns it. Do not set, switch, or "temporarily" use it, do not say it was set as the working org, do not call any tool with its IDs, and keep the existing selection unchanged. Never validate a switch against the inventory.
- **Require a developer or admin role to operate in an organization** - before any Console or I/O Events operation in an org, read that org's `role` from the account-scoped result (`includeAllAccounts: false`). If it is empty, missing, or `user` (case-insensitive), do not call any operation tool for that org. Tell the user that no operations can be performed for that user type in this organization and that they need the developer or admin role there. Do not retry, work around the check, or switch to another org or tool on the user's behalf; they may choose a different organization where they hold that role. Listing organizations is not an operation and is unaffected.
- **Stop inaccessible operations or unresolved working-org context** - if the account cannot be matched or the requested operation's org is outside it, report the error rather than using the all-account inventory as a fallback allowlist. Reauthentication is needed to change the authenticated account; after it, reload account-scoped organizations and discard stale resource context.

## Developer Terms Consent (Console and Events)

- **Org-scoped tools check Adobe Developer Terms first** - every Console and I/O Events tool that acts on an organization first checks that the terms are accepted and current for that org. If a tool replies that the terms must be accepted or re-accepted, nothing was executed.
- **Get explicit agreement, then accept** - show the terms link from the reply and ask the user to review it and explicitly confirm agreement, following the interactive feedback rule. Only after that confirmation call `accept_developer_terms` for that organization, then retry the original operation once. Do not infer consent from the original request, accept on the user's behalf unprompted, or reuse agreement given for another organization.
- **Stop if consent is declined** - report that the operation was not performed. Do not retry, work around the check, or switch to another tool to do the same operation.

## Console and Event Workflows

- **Inspect local configuration through safe helpers** - prefer shared `cli-config.mjs` for compact CLI environment, sign-in status and selection metadata, and `app-config.mjs` for an existing app folder's linked project and action metadata. Where linked into the skill, run `node "<skill-dir>/scripts/lib/cli-config.mjs"` or `node "<skill-dir>/scripts/lib/app-config.mjs"` with no arguments, or use the skill-specific wrappers. Setup's `config.mjs` provides broader sanitized details only when the workflow needs them. These modules can also be imported by skill scripts without printing output.
- **Keep local CLI credentials out of tool results** - do not expose credential-bearing CLI configuration, including full `aio config list` output, `aio config get ims` or its child paths, or Runtime authentication values. Verified metadata-only reads, such as `aio config get console --json`, are permitted when explicitly specified by the workflow. Do not inspect raw `aio app info` output or `.aio`/`.env` contents directly. For Runtime properties or CLI sign-in, follow `app-builder-setup` and use its dedicated `runtime-properties.mjs` and `login.mjs` helpers; do not inspect broad `aio rt property get` (or its aliases) or token-returning login output directly. Never bypass these helpers when they fail. Configuration helpers filter output before it reaches the assistant; login discards both output streams. This applies to assistant-run commands, not instructions for a developer working privately in their own terminal, and does not prohibit other workflow-approved `aio` commands.
- **Do not assume undocumented behavior** — if a behavior, field, or API detail needed by the workflow is unclear or not covered in the skill, call `search_adobe_docs` to look it up in official Adobe documentation before proceeding.
- Never ask for information you can fetch automatically.
- When a skill requires displaying IDs, always pair each ID with its name; never show a raw ID alone. If the skill calls for names only, keep IDs internal.
- Whenever `get_credentials` is called, immediately call `get_credential_services` for each returned credential before presenting credentials or subscriptions. Use only credentials returned for the selected workspace; do not include org-level credentials.
- If a tool response includes `console_url`, display it as a clickable link: `🔗 View in Adobe Developer Console: {console_url}`.

## I/O Events Workflows

- Never show `client_secret` values.
- Never guess `event_code` or `provider_id`; always fetch them from the API.
