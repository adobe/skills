# Fixture provenance & known limitations

`fixture/` is a hand-authored realization of this eval's Setup section:
the fictional B2B bookkeeping site ("Ledgerline") after extract, direct
and a partial prototype pass — `home` and `pricing` `approved` with
proposed files, `about` / `features` / `contact` `directed`, canon
written, no `stardust/migrated/`. It lives OUTSIDE the fixture tree on
purpose; everything under `fixture/` is copied verbatim into the eval
workspace.

## How it was built

Layered on `../prototype-before-after/fixture/` (post-direct state; its
`fixture-notes.md` covers `PRODUCT.md`, `DESIGN.md`, `DESIGN.json`,
`stardust/direction.md` and the directed `state.json`), which in turn
layers on `../direct-from-phrase/fixture/` (post-extract state and every
file under `stardust/current/`). Added here:

- `stardust/prototypes/home-proposed.html`,
  `pricing-proposed.html` — `prototype/reference/proposed-file-shell.md`:
  `stardust:provenance` comment as the first child of `<head>` (with
  `foldBackDecision` from the approval), inlined favicon, the `:root`
  block first in the first `<style>` with every token
  `stardust/reference/token-contract.md` requires (hex, matching
  DESIGN.md), `data-section` / `data-intent` / `data-layout` on every
  section (`stardust/reference/data-attributes.md`), no external CSS or
  JS except the sanctioned ≤10-line mobile-nav script. Content —
  headings, body copy, CTA labels and hrefs, nav labels, prices, FAQ
  pairs, the quote, logo alt text — is verbatim from
  `stardust/current/pages/<slug>.json`; nothing is invented, so
  `unsourcedContent` is empty. Media is referenced relatively from the
  prototypes directory (`../current/assets/...`) so migrate has real
  asset references to rewrite and copy.
- `stardust/canon/header.html`, `footer.html`, `canon.css` —
  `prototype/reference/canon-extraction.md`: the prototype's header and
  footer lifted verbatim (with `data-canon`), class-based compound CSS
  that only reads `var(--*)` tokens, each file opening with the
  `stardust:canon` provenance comment. Both prototypes contain the canon
  chrome byte-for-byte (the second approval logged no deviations).
- `DESIGN.json.extensions.canon` — same reference, § File structure:
  `sourceSlug`, `approvedAt`, `files{path, sha}` (**real sha256 of the
  files on disk**, not fabricated — migrate's idempotency check compares
  shas), `pinned` token paths, five compositional moves, two history
  entries (`first-approval`, `extension` with nothing added).
- `stardust/state.json` — `stardust/reference/state-machine.md`: the
  two approved pages carry `prototyped` and `approved` history entries
  and a `prototypePath`; the other three stay `directed`; flow keys
  present (`redesign`) so migrate's flow guard passes.
- `stardust/journal.md`, `stardust/status.jsonl` — four prototype
  entries (render, approve, render, approve) and their phase pairs.

The prototypes and canon are generated by one script so the chrome is
guaranteed identical across files; the script is not part of the plugin.
To regenerate, edit the files directly and recompute the three shas in
`DESIGN.json.extensions.canon.files`.

## Deliberate design choices

- **Footer links to slugs outside the inventory** (`/security`,
  `/careers`, `/help`, `/blog`, `/docs/api`, `/privacy`, `/terms`) are
  kept — a real site footer has them, and they exercise migrate's
  broken-internal-link flagging without breaking any page.
- **Canon exists already** so the eval measures migrate's Path A / Path
  B partition, not its canon auto-bootstrap. Delete `stardust/canon/`
  and `extensions.canon` to test the bootstrap instead.
- `type` stays `null` on every page (no `--prep` ran), so Path A′
  (template-applied siblings) is not in play; directed pages take
  Path B as the task expects.

## Known limitations — don't mistake these for skill bugs

- Everything inherited from the earlier fixtures: 1×1-pixel screenshots
  and media, fabricated content hashes in the extract JSON, no
  `brand-review.html`. Migrate copies the media files as-is; a visual
  check of the migrated pages will show 1-pixel images.
- Webfonts are named but never loaded; pages render with the system
  fallbacks. There are no `@font-face` rules for migrate to bundle.
- No `stardust/<slug>-shape.md` briefs exist for the approved pages;
  the content-aware stale rule falls back to the blanket rule if a
  re-direct happens (irrelevant to this eval).
- The `<script>` for the burger button is present in both prototypes
  and therefore in every migrated page.
