How the skill evals work

An agent skill is only useful if the model that runs it follows it. We run each skill on several models, grade the outcome with code, and report the lowest-tier model that does the job well enough, so the model choice is a measured decision instead of "always pick the biggest".

A run, end to end

Every number in the report comes from the same loop. The skill is copied from a git ref into a fresh workspace, promptfoo fans the work out over models, cases and repeats, and each run is a real agent session that uses the skill with a real headless browser.

The stack: what existed, what we added

We did not build an eval framework. promptfoo already provides the matrix, repeats, assertions and a viewer, and Pi already runs a model with tools and skills. What was missing was the glue between them, and the tests themselves.

Existing tools we rely on

  • promptfoo: test matrix, --repeat, assertions, the skill-used check, HTML export
  • Pi coding agent: SDK sessions, tool use, skill discovery, many model providers
  • playwright-cli and headless Chrome: the browser the skills drive
  • Chrome DevTools Protocol: for the cdp skills and for checking browser state
  • GitHub Actions and Pages: publishing the report

What we added

  • A promptfoo provider for Pi: isolated skills, per-run workspace and browser session, timeouts counted as failures, tool trace
  • 49 cases with code graders and ground truth, plus a fixture server and a headless shim for the extension skill
  • A baseline gate, per-skill floors, the report generators and a replay provider that renders results through promptfoo
  • A fix in browser-probe so parallel runs no longer share browser sessions (PR #407)

How a run is graded

No model grades another model. Each case has a ground truth, either a fixture page whose answer we wrote or a real site checked against its own live behaviour, and a grader written in code.

1. The skill was used

promptfoo's skill-used check. Pi has no skill tool, so reading the skill's SKILL.md counts.

2. The output is right

Files in ./out, the reply, or the tools' output, compared with the known answer: languages, forms, section counts, recipes.

3. The state is right

For browser tasks the grader inspects the agent's own browser session: is the banner really gone, does the recipe really load the page.

4. It was fast enough

Each skill has a time budget (usually 120 s). A slower run is aborted and counts as a failure. Broken output is a failure with a reason, never a harness error.

From runs to an answer

The baseline model runs first. If it cannot pass the suite, the problem is the skill or the eval, and other models are not run. The floor is the same for every model: at least 90% of runs pass within the time budget.

  • Stability: every case runs three times per model. A case is flaky when its repeats disagree, and the report counts those.
  • Cost: average dollars per run at the list prices configured in Pi, shown next to the pass rate.
  • Tier order: the order of models in models.yaml is a judgment call. "Lowest model" means the first one in that order that meets the floor.

The cost of the model choice

Skill, CLI, or neither?

The same cases run in three arms. skill + CLI: the skill is loaded and the web CLI is on PATH. CLI only: no skill is loaded or on disk, the CLI is on PATH, and the prompt adds one line: A `web` CLI is installed; `web --help` documents it. Neither: no skill and no CLI. Both comparison arms run in an empty workspace under a private home, and a grader fails any run that opens a skill file from disk (the skills are installed on this machine, so this is checked, not assumed). Their prompts also add the output format, meaning file names and fields, never how to produce them. Cases that hinge on a skill's own method are left out, every bar covers the same cases, and browser-probe is judged only on whether the recipe loads the page. To limit cost they run on a few models only. The report also records whether each CLI-only run actually called web.

Read it as: what the CLI adds over a clear output format, and what the skill adds over the CLI. These are comparisons on small samples, not benchmarks.

Browsers stay invisible

Evals must never open a window on the machine running them. Every agent shell refuses --headed and open, a grader fails any run that still tried, and a sweeper kills automation browsers started without --headless. The extension skill, which launches a headed Chromium by default, goes through a headless shim.

What the benchmark already found

  • browser-probe reused the same playwright-cli session names, so parallel probes broke each other. Fixed in the skill, with a test, in PR #407.
  • page-prep sometimes hit its time limit because a model read the screenshot in the same turn that took it, then searched the whole disk for the file.
  • Opus saved the page-tree node map in a leaner format than the skill's own. The grader first rejected it, which showed the check was too strict.
  • cdp-ext-pilot opens a headed browser by default. A shim now runs it headless so evals do not take over the screen.

What these numbers do not tell you

  • Small samples: 9 to 27 runs per skill and model. Differences of a few points are noise.
  • Live sites move: real sites change their bot protection, so results drift. Fixture cases do not.
  • One harness, one effort level: every model runs in Pi at low reasoning effort. Another harness or setting can behave differently.
  • List-price costs: they estimate cost, they are not an invoice, and subscription models are priced as if per token.
  • One skill version: results describe the git ref listed in the report, not later changes.
